# 文字处理结果与待确认状态

当前维修人员可为本人“处理中”的工单提交文字处理结果。提交成功后工单进入“待用户确认”，结果说明、提交人和提交时间在任务、本人报修及管理员详情中保持一致。

直接处理工单沿用原流程；需报价任务必须先确认报价、生成订单并开工，才能提交结果，不能绕过订单状态。报价型提交将订单同步置为待用户确认，状态与结果审计在同一事务。规则见 [QUOTES.md](QUOTES.md)。Web 在服务订单区复用同一结果表单，RN 暂未新增报价型结果入口。

## 入口与范围

| 入口 | 行为 |
| --- | --- |
| `/service/tasks/:id` | 处理中任务显示“提交处理结果”，确认框填写处理说明 |
| POST `/api/tasks/:id/result` | 首次成功和同意图重放均返回 201，返回当前任务 |
| 原有任务、本人报修与管理员详情 | 在各自原有数据范围内展示结果及操作记录 |

结果提交接口仅执行 **processing → confirming**。用户确认由独立本人接口执行，见 [TICKET_CONFIRMATION.md](TICKET_CONFIRMATION.md)；退回、修改已提交结果、维修结果照片或改派尚未实现。工单现场照片独立于处理结果，见 [TICKET_PHOTOS.md](TICKET_PHOTOS.md)。

## 权限与校验

RN 已通过 POST `/api/mobile/tasks/:id/result` 接入相同 DTO 和 TaskResultsService。原生表单使用 MutationModal、useApiMutation 与 canSubmitTaskResult，按规范化说明保持提交意图；关闭清理、异常重试及过期页面处理遵循下述规则。原生验证边界见 [MOBILE.md](MOBILE.md)，此前 Web 验证记录保留原日期与范围。

- 身份由有效会话确定；仅维修人员可提交，管理员和报修用户不能代提交。
- 先按工单 ID 与当前 assigneeId 验证归属，未分派给本人和不存在的工单统一返回 404；历史成功意图不能绕过当前归属。
- 请求包含 requestId、expectedVersion 和 description。提交编号须为 UUID v4；说明去除前后空白后必须非空，最多 2000 字符，保留内部换行。
- 操作人、时间与目标状态由服务端确定；actorId、status、attachments 等额外字段被拒绝。
- 非处理中状态或版本过期返回 409；说明、编号、版本格式错误返回 400。会话过期或账号停用返回 401。

## 事务、幂等与审计

TicketResult 保存处理说明、操作人、数据库时间、工单、提交编号和原版本；当前 ticketId 唯一，actorId 加 requestId 唯一。

1. 验证当前角色和归属后，查找相同操作人/提交编号的历史记录。
2. 工单、原版本及规范化说明全部一致时返回当前任务；编号对应不同工单、版本或内容时返回 409。
3. 新提交在同一事务内按 `id + assigneeId + processing + version` 条件更新为 confirming、递增版本并写入结果。
4. 竞争失败后核对已提交意图，同意图返回原结果，不同意图返回冲突。结果唯一约束失败时状态更新也回滚。

已提交说明不可覆盖，重复请求不改变原提交人或时间。任务、报修和管理员响应通过同一字段白名单与序列化函数读取结果，不暴露请求编号、命令原版本或数据库内部字段；任务及本人详情的当前版本用于后续命令并发控制。

当前仅保存一次结果。后续支持退回与再次提交前，应按批次扩展结果记录、保留历史，而非覆盖原说明或绕过现有唯一约束。

## 前端交互与复用

- MyTaskDetailPage 组合 SubmitTaskResultModal，提交入口统一由 canSubmitTaskResult 判断；状态和权限仍由服务端独立校验。
- 表单管理说明和错误，关闭重开清空。提交期间禁用关闭与重复操作；离页取消请求，超时后允许重试。
- 相同规范化说明在当前弹窗内重试沿用提交编号，修改说明或重新打开产生新意图；结果不明时应先重试原内容或刷新核对。
- 版本冲突保留输入并提示关闭、刷新；不会自动覆盖另一窗口已提交的结果。
- 结果作为纯文本显示，保留换行并支持长文本换行；三种角色复用 TicketRecordDetails，不引入 HTML 渲染或独立管理员副本。
- 成功后刷新任务，移除结果提交入口并显示待确认状态；确认按钮仅出现在报修用户本人的详情，维修人员与管理员不能代确认。

## 验证与迁移

```sh
npm run verify:results
npm run verify:results-ui
```

Windows 使用 `.\scripts\npm-local.ps1 run <脚本名>`，先启动专用本地数据库、API 和 Web。只新增结果表及约束；迁移前备份到被忽略的 `.local/backups`，不修改旧迁移或重置数据。

API 检查覆盖归属与角色、说明长度和去空白、过期版本、八路并发、不同说明竞争、唯一冲突回滚，以及三角色响应一致性。浏览器检查覆盖关闭清理、空白校验、手机表单、多行结果、响应丢失重试、状态过期冲突、刷新和越权读取。

临时工单和账号通过共享 taskFixtures 工具按本轮随机 ID 清理，结果记录随工单级联清理；不会按名称、角色或标题批量清理人工数据。截图可包含测试后已清理的临时记录。验证范围为本地浏览器和真实数据库，不代表生产环境或原生客户端交付。

- 原有登录/设备、本人报修、管理员分派和维修任务/接单 API 与浏览器检查，以及独立演示页面回归均通过。
