# 报修用户确认完成

报修用户核对处理结果后，可将本人的待确认工单确认为已完成。状态、确认人和数据库时间在同一事务中写入，管理员与当前维修人员通过原有详情读取完成记录。

## 入口与契约

| 入口 | 行为 |
| --- | --- |
| `/service/tickets/:id` | 本人待确认详情显示“确认完成”，弹窗展示处理说明和结束提示 |
| GET `/api/tickets/:id` | 本人详情新增当前 version，返回 ReporterTicketRecord，用于确认并发控制 |
| POST `/api/tickets/:id/confirm` | 首次成功及同意图重放均返回 201 和当前本人详情 |
| 原管理员及维修任务详情 | 只读展示确认人、时间及已完成状态 |

本人列表继续返回 TicketPage，列表项不新增 version。原有字段与数据归属保持一致；详情和确认响应中的 version 为当前业务版本，不包含请求原版本或幂等编号。

## 权限与状态约束

- 未登录返回 401，管理员与维修人员不能代确认，返回 403。
- 工单 ID 与当前会话报修人 ID 必须匹配；未知或他人工单统一返回 404，包括旧意图重放。
- 唯一新增状态操作为 **confirming → completed**，须有真实处理结果、版本匹配且无已有确认记录。
- 请求仅含 UUID v4 requestId 和整数 expectedVersion；操作人、时间、目标状态及处理结果不能由客户端指定。
- 版本过期、已完成、其他状态或缺失处理结果返回 409，保持原记录；格式错误和额外字段返回 400。

不开放管理员代确认、自动完成、撤销、退回、再次提交或重新打开入口。设备授权或启用状态的变化不撤销已提交报修的本人历史查询与确认权。

## 事务、重放与终结状态

TicketConfirmation 保存工单、确认人、时间、提交编号和原版本。ticketId 唯一，同一确认人加 requestId 唯一。

1. 先验证报修角色和当前归属，再查询已提交意图。
2. 同一意图的工单、原版本一致时返回当前详情；编号对应不同工单或版本时返回 409。
3. 新确认在同一事务内按 `id + reporterId + confirming + version`、结果存在、确认记录不存在的条件更新为 completed、递增版本并写确认记录。
4. 并发竞争失败后核对已提交意图，同意图返回原结果，不同意图返回冲突；失败不能留下部分状态更新或重复确认记录。

确认不改写维修说明、原提交人或提交时间。已完成工单的新分派、接单、结果提交和重复确认意图均被拒绝；原成功意图的重放只返回原结果，不再更新状态或时间。

## 前端与工程边界

- ConfirmTicketModal 展示处理结果摘要及验收含义，取消不改变状态；提交期间禁用关闭与重复操作，离页取消请求，超时后允许重试。
- 当前弹窗固定提交编号，结果不明时沿用原意图重试；关闭重开后应先刷新核对。
- 版本冲突保留提示，关闭并刷新后显示实际完成记录。不同路由或账号切换会卸载旧内容与弹窗。
- 确认入口共用 canConfirmTicket；三角色复用 TicketRecordDetails 的确认人、时间和成功提示，没有另外维护管理员副本。
- TicketConfirmationsService 复用 TicketsService 的报修角色/归属读取，使用 TicketCommandDto 的请求格式校验；接口白名单和序列化仍归工单模块。
- 本次迁移只新增确认表与约束；已有账号、工单和旧迁移保留，迁移前备份至被忽略的 `.local/backups`。

## 验证

```sh
npm run verify:confirmations
npm run verify:confirmations-ui
```

Windows 通过 `.\scripts\npm-local.ps1 run <脚本名>` 执行，先启动专用本地数据库、API 与 Web。

API 检查覆盖角色、归属、参数、缺失结果、非法状态、版本、八路同意图并发、不同意图竞争、三角色一致性及完成后的不可重开。浏览器检查覆盖取消、手机确认框、响应丢失重试、刷新、过期页面、列表完成状态和只读角色。

临时工单按本轮随机提交编号和报修人清理，确认记录随工单级联清理；临时账号只按本轮随机 ID 删除，不按标题或角色清理人工数据。截图可能包含已清理的临时记录。

本地最小文字链路贯通：报修 → 分派 → 接单 → 处理结果 → 报修用户确认完成。该验证不包含真实硬件、原生客户端、独立安装包或生产环境交付。
