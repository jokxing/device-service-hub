# 文字报修与本人记录

当前报修入口为：**报修用户登录 → 授权设备旁点击报修 → 填写文字 → 创建待分派工单 → 查看本人列表与详情**。管理员首次分派与维修人员接单已接入真实后端，见 [ADMIN_ASSIGNMENT.md](ADMIN_ASSIGNMENT.md)、[TECHNICIAN_TASKS.md](TECHNICIAN_TASKS.md)；本人记录可查看分派与接单人员、时间及处理状态。图片上传、处理结果及确认仍属于后续步骤；完整流程演示与真实数据分开。

## 页面与接口

| 入口 | 行为 |
| --- | --- |
| `/service/devices` | 在启用设备旁发起报修，仅报修用户显示入口 |
| `/service/tickets` | 本人报修列表，分页状态保存在 URL |
| `/service/tickets/:id` | 本人报修详情，可刷新回看 |
| POST `/api/tickets` | 首次成功返回 201；同意图重放返回 200 和原记录 |
| GET `/api/tickets/mine` | 本人分页列表，默认每页 10 条，最多 50 条 |
| GET `/api/tickets/:id` | 本人详情；不存在和未授权记录都返回 404 |

创建请求包含 `requestId`、`deviceId`、`title`、`description`、`priority`。`requestId` 为 UUID v4；标题最多 60 字符，描述最多 500 字符；文字前后空白会被去除，空白内容拒绝。优先级限定普通或紧急。

报修人由已验证的会话确定。客户端不得提交 `reporterId`、`status`、分派人等字段；额外字段会被 DTO 校验拒绝。

## 角色与设备规则

- 只有报修用户可以使用创建、本人列表与详情接口。管理员通过独立管理接口查询与分派，维修人员通过独立任务接口查询与接单；不会放宽本人报修接口的数据范围。
- 新报修必须关联本人获授权且启用的设备。未知/未授权设备返回 404，已授权但停用的设备返回 409。
- 已提交的本人报修保留查询权，即使后来设备停用或撤销设备访问授权；这不会开放设备详情接口或他人的维修记录。
- 工单初始状态固定为 `pending`（待分派）。管理员首次分派后转为 `assigned`（待接单），对应维修人员接单后转为 `processing`（处理中）；报修用户不能直接修改状态。
- 列表查询和总数使用同一个本人条件，详情条件同时包含工单 ID 和登录用户 ID。响应只含本人记录和必要维修人员信息，不暴露提交摘要、提交编号或管理员审计详情。

## 防重复提交

`Ticket` 保存报修人、设备、正文、优先级、状态、时间，以及内部 `requestId`、`requestHash`。数据库唯一约束为 **`reporterId + requestId`**。

1. 前端为当前表单内容保留一个提交编号，相同内容在结果不明时重试沿用它；改内容或重新打开表单是新意图。
2. 后端对经过校验、去空白后的业务字段计算摘要；已存在且摘要一致则返回原工单，摘要不一致返回 409。
3. 新请求在事务中检查设备授权和启用状态，再插入工单。角色、报修人、初始状态不信任客户端。
4. 并发请求都尚未看到已有记录时，由数据库唯一约束裁决。失败方处理 Prisma `P2002`，读取胜出记录并重新核对摘要。
5. 已成功请求的重放只返回原结果，不因设备后来停用而再次创建或修改工单。

防重针对同一用户的同一提交意图，不按“同设备/同内容”全局合并报修。提交编号在当前弹窗内保留，不是离线同步；刷新或重开表单后若先前结果不明，应先查看本人记录。

展示编号由数据库序号生成，如 `WO-000001`；并发冲突或回滚可能留下序号间隔，序号不代表工单总数，也不是防重依据。

## 工程边界

- `modules/tickets` 包含 Controller、DTO、Service、常量、投影和序列化/摘要方法；未增加通用 Repository。
- `packages/contracts` 共享创建输入、记录、分页、状态和优先级类型；DTO 继续承担服务端运行时校验。
- ServiceLayout 共用真实身份、退出与导航；Web 的 `useApiResource` 负责读取请求取消和失效处理，不依赖具体业务模块。
- `TicketTextFields` 只共享字段展示，演示提交和真实 API 提交仍各自实现。前端加载、表单和详情按职责拆分。
- 创建和列表在服务器执行数据归属判断；前端隐藏按钮不构成权限保障。

## 运行与验证

升级已有本地数据库前先保留备份，然后使用 `npm run db:migrate` 应用新增迁移，不修改旧迁移或使用 reset。本阶段已在被忽略的 `.local/backups` 创建升级前备份。

环境和账号说明见 [API_SETUP.md](API_SETUP.md)。启动数据库、API、Web 后：

```sh
npm run build
npm run test:business
npm run verify:api
npm run verify:connected-ui
npm run verify:ui
npm run verify:tickets
npm run verify:tickets-ui
```

- `verify:tickets` 覆盖权限、参数、防重、八路并发、同编号不同内容竞争、停用/撤权、本人分页与越权详情。只针对专用本地库，临时账号/设备状态在 finally 恢复，临时工单按本轮随机提交编号清理。
- `verify:tickets-ui` 模拟“服务端已提交但浏览器未收到响应”，验证同表单重试只产生一单，并检查本人列表、详情、刷新、换账号和窄屏。截图包含临时验收记录，测试后清理。
- API 验证保留一个仅存在 `.local` 的待复核记录。重启 API/数据库后执行 `npm run verify:tickets:restart`，检查报修、会话和重放结果；成功后撤销测试会话并清理临时工单。
- 当前 Windows 本地命令仍通过 `.\scripts\npm-local.ps1 run <脚本名>` 执行，所有临时数据位于项目内。

页面标题、说明和返回入口统一使用 ServicePageHeader。服务布局负责左右边距，避免全局 main/nav 样式造成窄屏二次缩进；详情返回入口使用带边框的链接，桌面在标题右侧，窄屏自动换行。此次布局调整已通过构建、真实设备/报修浏览器回归及原演示页面回归，并查看桌面和 390px 详情截图。

人工验收可使用 `reporter.a` 创建一条报修，刷新后查看，再退出并用 `reporter.b` 检查其列表不含该记录。人工创建的数据不会被自动验收脚本按标题或账号批量删除。
